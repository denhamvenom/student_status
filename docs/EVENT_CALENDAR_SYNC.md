## Behavior and recovery

Only Coach/Travel Lead can manage connections. Stable Calendar identifiers and transactional claims prevent duplicate links. Creation retries reuse a deterministic identifier. Conditional writes refuse concurrent Calendar changes. A conflict offers Reload Calendar details explicitly, discarding the unsynced app changes; the editor also refuses stale local drafts. An unavailable initial selection can be replaced before a link is established.

Existing entries retain their details on connection. Timed and all-day occurrences are supported; repeated entries link to one occurrence. All-day schedule dates are edited in Google Calendar, while their changes sync back into the app. Managed media text preserves other description content. Linked changes use the existing minute Calendar polling; full resets reconcile linked entries directly. Calendar identity and observation/revision checks fence stale or changed-source data.

Material title/location/schedule/cancellation changes preserve signed originals but require new permission coverage. Earlier schedules clamp signup/room deadlines to the new start. Cancellation remains visible and stops new signups, approval, enrollment, new consent forms and readiness claims. Running/failed Whole Team assignment terminates as cancelled without erasing processed participation or charges. Financial correction and withdrawal history remain available; no automatic refund is implied.

## Recurring series (RRULE) — November 2026

This supersedes the October 19 rule that only individual occurrences are handled, but only for app recurring series (`eventSeries`). One-off events still link to one occurrence. Sources: `convex/eventSeries.ts`, `convex/eventSeriesCalendar.ts`, `convex/lib/seriesGenerate.ts`, `convex/lib/rrule.ts`. Audience and series behavior is described in [EVENT_AUDIENCES_AND_SERIES.md](EVENT_AUDIENCES_AND_SERIES.md).

**Hard rule:** never PATCH an existing master's start, end, summary or location. Google applies a master edit to every instance, past ones included, and past instances back Timeclock occurrences and attendance. The only write to an existing master is a recurrence PATCH that sets `UNTIL`, or a DELETE when the master has no past instance.

- **Mapping:** one app series is one Google recurring master. Its id is `"sr"` + the first 40 hex characters of SHA-256(series id) (a valid base32hex id, new for every series document and so for every split). The master is created with one POST: summary, location, Chicago local start/end with `timeZone: America/Chicago`, `RRULE:FREQ=WEEKLY;INTERVAL=n;BYDAY=…[;UNTIL=…|COUNT=k]`, and `extendedProperties.private.studentStatusSeriesId`. A 409 response is recovered by reading the master and checking that property. The master id is claimed uniquely in `eventSeriesCalendarClaims`.
- **Instances:** instance ids are always read from `events/{master}/instances` (canceled ones included) and never synthesized. Each meeting row links one instance: `calendarChoice: "link"`, `calendarEventId` = the instance id, an `eventCalendarClaims` row, and `calendarRecurring: true`. The row key is the Chicago date of the instance's `originalStartTime`. A Google single-instance edit or cancellation flows through `applyObserved` and marks the row detached or cancels it. A whole-series Google edit yields one notice per series, not one per meeting. An instance on a day outside the rule sets the series to `needsReview`.
- **This meeting only:** the existing single-event push PATCHes the instance with `if-match`, and Google stores it as an exception.
- **Split ("this and following" at meeting K):** create the new series' master, then re-point rows ≥ K and their claims to the new instances (dropping stale old-master claims), then PATCH the old master's recurrence to `UNTIL = start(K) − 1 s` (any COUNT becomes UNTIL) with `if-match` on the master etag. If the old master has no past instance, it is deleted. Re-pointing runs before truncation, so the old instances' cancellations find no claim and cause no false cancellation, unenrollment or notice. After every master write, fresh instance etags are stored so the next refresh does not re-notify. A 412 or a recurrence changed in Google sets the series to `conflict`.
- **Daily reconcile** (`extendAndReconcile`, from the daily cron): reads the master. A deleted master, or a changed repeat rule or start (for example a Google-side "this and following", which creates a new master), sets `needsReview`. Otherwise it creates and links missing window rows.
- **Adopting an existing Google series (Coach only):** `googleSeriesCandidates` lists running masters that are not yet claimed. Supported masters are timed, `America/Chicago`, with exactly one `FREQ=WEEKLY` RRULE (plain BYDAY, optional UNTIL/COUNT); other rules are refused with a named reason. `adoptGoogleSeries` reads only and makes **no Google write**. It stores an `origin: "adopted"` series and links window rows to the existing instance ids. A meeting already connected as a one-off event is converted in place, not duplicated. No notifications are sent.
- **Tuesday attendance:** Timeclock occurrences use the Google instance id as `sourceKey`, and events join them through `eventCalendarClaims.calendarEventId`. Adopting the existing Tuesday Google series therefore keeps past and future Timeclock sessions attached without new `attendanceMeetings` rows. Do not create a second, app-owned Tuesday series while the Google one exists: new instance ids would create duplicate Timeclock occurrences and orphan history. The duplicate guard in `eventSeries.create` refuses that overlap. (VERIFY on production) Tuesday `timeclockOccurrences` carry `recurringEventId`; this has not been checked against live data.
- **Write gates:** the gates are the same as for single events. Series Calendar writes need `STUDENT_STATUS_CALENDAR_WRITE_ENABLED` and the production URL. Otherwise `addToCalendar` and splits of a Calendar series are refused with a plain message.

## API references

Implementation follows Google's [event insertion contract](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [event listing contract](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), and [conditional updates with entity tags](https://developers.google.com/workspace/calendar/api/guides/version-resources). Retries must reuse the same calendar event identity; concurrent edits must not silently overwrite changes.
