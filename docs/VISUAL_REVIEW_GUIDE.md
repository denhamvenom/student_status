# Visual review guide

Open http://localhost:5173 in the existing signed-in Chrome windows. Review appearance, clarity and the connected workflows; there is no need to repeat payments, signatures or permission changes.

Start with corrected family Home/Money, account/report opening, empty New Event validation and accepted-permission Readiness. The Parent presentation has now been checked live after sign-in. Do not repeat payments or signatures.

1. **Coach: Team → student record.** Check roster filters, profile/link status, financial summary, attendance and upcoming-event readiness.
2. **Coach: Events → Readiness.** Check event information, room/transport controls and printable summary. Incomplete evidence should be clearly Draft or unavailable.
3. **Coach/Travel Lead: Money and Reports.** Review account history, fee order and report detail. Available funds means unspent personal plus fundraising money; it is different from the fundraising-only travel balance.
4. **Parent: Profile & health → Forms.** Review the populated PDF and accepted receipt. The approved original logo, wording and normal one-page layout remain. The deliberately verbose rehearsal fixture has a necessary continuation; ordinary-length examples remain one page. Do not create a real signature.
5. **Student and Mentor:** Check Home/report, navigation, own profile and lower-page controls. Student withdrawal recovery should lead back to the event.

The hosted prototype remains the style reference. Later additions—complete account records, administration, scoped reports, truthful Draft/unavailable states and the approved PDF—are intentional. Development fixture names and the development banner remain honest; they are not production onboarding content.

Evidence limits: recipient room acceptance and no-linked Parent were reviewed through existing source/tests rather than a new live account. Existing Parent links and permissions were preserved. The user confirmed PDF and CSV open correctly. Friendlier CSV cents headings/units are deferred until after launch by request.

Visual approval does not authorize main merge, production deployment, real signing or destructive retention. Launch additionally requires domain/sign-in ownership, privacy/retention configuration, backups/restoration, monitoring/rollback, real onboarding and demo transition.
