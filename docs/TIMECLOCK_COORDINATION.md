## Proposed shared backend contract

All names below are proposals, not deployed schema. Use server timestamps, indexed lookups, runtime argument/return validators and server authorization for every public operation.

| Entity | Proposed contract |
| --- | --- |
| Calendar source | Single configured calendar, timezone America/Chicago, server-only credential reference, sync status/cursor/last success. Future Coach settings in Student Status. No calendar owner identifier in committed fixtures. |
| Calendar occurrence | Source calendar + Google occurrence ID; recurring series/original-start metadata; scheduled start/end or all-day dates; title, cancelled state, provider version, observed time and append-only schedule revisions. Keep identity when an occurrence moves. Manual occurrences have a separate internal source/ID. |
| Attendance event session | One shared runtime session per occurrence, state unopened/open/closed/cancelled, schedule revision, scheduledStart/End, effectiveEnd, extension total, optional attendanceMeeting/travel-event link. Opening an all-day occurrence atomically establishes one start and operator-selected end; concurrent devices reuse it. Unscheduled name/duration creates a shared occurrence/session. No per-device duplicate event sessions. |
| Device console | Opaque non-auth device identifier plus selected event; shared event status is authoritative. Selection is ephemeral UI state, not authority. One selected event per device; confirm whether multiple browser tabs on one device must be coordinated. No cached roster or offline queued writes initially. |
| Clock interval | studentId, eventSessionId, in/out server timestamps, opening/closing actor or system reason, command ID and schedule revision. Returning creates a new interval. Keep original evidence; corrections do not erase it. |
| Active student session | One indexed lock/pointer per student. Every clock-in/transfer reads and updates the same row in a transaction. Convex indexes are not uniqueness constraints: enforce query-and-insert invariants transactionally. Confirmed transfer closes the old interval and opens the new at the same timestamp, checking the expected old interval so stale confirmation fails. |
| Extensions | Append actor, server time, added duration, old/new end and command ID. Validate active operator and PIN on server, rate-limit failures and audit successes without logging PIN. Initial PIN supplied privately by owner; do not embed it in source, client bundle, docs or fixtures. Store protected server configuration, with a future rotation path. |
| Corrections | Coach-only append-only changes with reason, actor/time, before/after, revision and void markers for erroneous records. Add missed intervals rather than deleting history. Reject negative times/overlaps; whether a Coach may override qualifying attendance is still undecided. |
| Attendance summary | Derived/versioned per student and attendance event: total, early, scheduled, extended milliseconds, longest scheduled uninterrupted interval, qualifying flag, source/correction state. Student Status owns views, classification and administration. Preserve legacy boolean/import records as identified legacy evidence; never invent one-hour intervals. |

Commands: open occurrence; create unscheduled event; clock in/out; confirmed transfer; group in/out; clock out all in selected event; extend event; Coach correction. Each uses an idempotency key and explicit stale-state checks. Group conflicts must be previewed and explicitly confirmed before transfers; propose all-or-nothing bounded batches rather than silently skipping students. Clock-out-all operates on the current server set for that event, with a documented batch bound and race handling. Queries return minimal today-event, selected-console and sorted-roster projections.

Qualification for each interval is its overlap with the applicable scheduled window: `max(0, min(out, scheduledEnd) - max(in, scheduledStart))`. Attendance is true only if at least one uninterrupted interval overlaps for at least 3,600,000 ms. Separate visits never combine to qualify. Total time may sum visits; early/scheduled/extended portions are separate and reconcile to total within the event's effective bounds. Decide how schedule revisions affect historical classification before implementing recalculation. Attendance is independent of travel signup.

Closing: schedule an internal Convex mutation for effectiveEnd, without a browser dependency. Each job checks current session revision/end so an old job cannot close an extended event. Store effective close timestamp, not delayed job execution time. Every clock mutation also rejects/settles expired sessions if the worker is delayed. Queries subscribe to closed state; connected consoles return to event selection, and reconnects reconcile. Do not promise millisecond-exact job execution. All-day concurrent-open and extension/auto-close races need explicit tests.

Calendar synchronization: server-side action fetches Calendar and internal mutations apply versioned changes atomically. Keep cancellation and moved-instance evidence, handle pagination, invalid sync-token full reconciliation, and expose stale/error state. Do not delete sessions when a calendar event disappears. Select today's overlapping events using America/Chicago day boundaries/DST, preserve finished entries but disable normal opening; cross-midnight sessions need an explicit visibility rule. Polling cadence and outage behavior remain decisions.

## Multi-app authentication and calendar authorization

Keep existing verified Google identity integration and single deployment Google callback at `https://third-bandicoot-18.convex.site/api/auth/callback/google` for development. Do not create a second identity system or switch auth libraries. Current installed Convex Auth uses one SITE_URL and its default redirect permits only relative paths/the same base. Future multi-app sign-in needs an exact parsed origin/path allowlist in the auth redirect callback, deliberate redirectTo per app and tests rejecting arbitrary origins, protocol-relative URLs and preview hosts. Verify both app sign-in round trips before enabling either deployment. No redirect setting changed here.

Use separate origin-local browser sessions (different dev ports, distinct production origins) and explicit per-app storage namespaces. Do not share tokens by parent-domain cookies, URL forwarding or copied localStorage. Installed provider defaults to localStorage; shared-device session persistence/signout needs a deliberate policy. A common database/token issuer does not grant new permissions: every backend function must check the operator. Existing user permissions still apply to that user; hostname alone cannot make a token application-scoped. If stronger per-app token restrictions are required, design that explicitly rather than claiming CORS/redirect settings enforce them.

Calendar read authorization is separate from Google login. Prefer a dedicated service identity with read-only access to the one selected calendar if the owner can share it; otherwise a separate authorized Coach connection with server-only refresh credentials and minimum read scope. Do not request Calendar access from every operator. Credentials, calendar settings, provided PIN and account identifiers stay outside committed documents and fixtures. Future credential/configuration changes require the normal authorization step.
