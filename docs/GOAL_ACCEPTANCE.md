## Decisions versus implementation defaults

1. **Whole Team timing is resolved.** The user confirmed all active members at creation and automatic later additions to upcoming events only. Started/past events do not gain later joiners. Reactivation adds a missing membership only while preserving existing participation and approved withdrawal history; do not reverse a reviewed withdrawal or create historical debt. A financial/capacity conflict needs an explicit, reviewable response rather than silently dropping required members.
2. **Permission wording/products approval is a later real-signing gate.** Pain, Allergy and Cold categories with Allow / Contact me first / Do not allow, nothing preselected, and the named organizations/minor-first-aid requirement are settled. Build concrete synthetic forms, versioned snapshots, correction/paper/export workflows now. Final products, exceptions and administration wording require Coach approval before any real signature can be accepted. Do not reduce this task to another static draft.
3. **Retention scope is a deletion gate.** Five years from the most recent account archival is settled, including reactivation followed by another archive (October 13 decision). Coverage, backup/export treatment and holds remain unresolved. Build inspection/preview and hold controls with precise unresolved policy labels; preserve records until actual deletion is authorized and tested. A preview is not implemented deletion.
4. **Ordinary engineering choices are defaults, not blocking questions.** Use existing Base UI components, shared tokens/copy, Convex auth-derived actors, integer cents, append-only evidence, existing same-season access patterns and guarded synthetic fixtures. Use additive schema changes compatible with existing data. Ask only when a domain outcome would otherwise be invented.
5. **Evidence access is distinct from policy.** Missing authorized Mentor/Travel/Parent account states or unreliable captures are verification blockers, not a reason to mark scope complete. Prefer already authorized accounts and explicit synthetic setup. Do not change live account privileges solely for convenient screenshots without authorization.

## October 13 integration architecture decisions in progress

The active implementation branch is now `feature/student-status-completion`, separated from the frontend-only PR ancestry. The user confirmed automatic later Whole Team additions apply to **upcoming events only**. Started/past events do not gain later joiners. Existing participation and approved withdrawal history remain preserved. Earlier text identifying the time cutoff as pending is historical.

A review of initial bounded implementations found that multiplying independent bounds is not a safe transaction budget: 500 students times their ledger/charge histories, or 500 sessions times interval/correction histories, can exceed database limits even though each individual query is bounded. The following architecture is proposed for integration-owner approval, not represented as implemented:

- Whole Team activation uses an event participant-row count maintained atomically by every relevant insertion, plus one batched financial operation per student. Read that student's existing ledger/charges once; create missing event fees, preserve source allocation and commit membership/charges together. Status-only changes do not change participant-row counts. A missing old counter requires reconciliation before use.
- Creating a Whole Team event with up to 500 members uses durable provisioning: save the bounded creation-time member list, process one student atomically per scheduled step, and checkpoint progress together with the next scheduled step. Concurrent later joins remain idempotent. Surface pending/failed enrollment and retry; readiness cannot silently describe a partially provisioned roster as complete.
- Finance reports use transactionally maintained per-student financial summaries, with season aggregates and verified backfill. Every financial writer, including withdrawals, payouts, both sides of transfers and synthetic fixtures, maintains the summaries in its transaction. Unknown/unbackfilled data is unavailable rather than a misleading zero or partial team total. The ledger remains the authoritative financial history.
- Attendance uses per-student/per-session derived summaries tied to a source revision. Interval, correction, close/cancellation and schedule changes invalidate the report revision. A resumable worker derives one student's session evidence per step. Reports distinguish current verified totals, provisional open-session time and summaries still updating; stale summaries never silently pass as verified. Raw correction reasons remain restricted.

Integration must verify worker retry/idempotency, counter/aggregate consistency, write-hook coverage, stale revision handling, backfill completeness and realistic maximum-data budgets. A successful mocked small-fixture suite does not establish transaction-limit support. Existing financial-history limits remain explicit until a separately verified migration expands them.
